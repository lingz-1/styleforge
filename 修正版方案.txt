# 定稿版方案书：StyleForge v3.2.1-final

> **版本：v3.2.1-final** | **日期：2026年8月5日**
>
> **状态：✅ 方案冻结，可进入开发**
>
> **后续仅允许调整**：Prompt措辞、Few-shot示例、检索权重（五类权重值）、评审阈值。**禁止变更**：三Agent职责边界、request_signature结构、四决策分支、回退次数上限。


## 一、项目定位

**StyleForge：语义驱动型三智能体决策图**

StyleForge 是一个基于 LangGraph 的语义驱动型三智能体穿搭系统，通过请求特异性建模、多查询衣橱检索、上下文条件化组合和比较式评审，实现对不同语境高度敏感且避免日常化坍缩的个性化搭配推荐。

**核心目标**：
- 不同用户请求应改变检索空间、候选组合和最终推荐
- 避免所有请求退化成相似的日常基础搭配
- 推荐结果与用户完整语义匹配，而非压缩后的标签


## 二、架构全景

```
用户请求
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ Agent 1：语义检索 Agent                                    │
│ 输入：用户请求 + 衣橱统计摘要 + 历史推荐摘要 + 检索工具     │
│ 输出：request_signature + retrieval_plans + Top-50 候选    │
│ LLM调用：1次                                              │
└─────────────────────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ Agent 2：搭配组合 Agent                                    │
│ 输入：用户请求 + Top-50 候选 + request_signature          │
│ 输出：3-5 套搭配方案 + composition_strategy               │
│ LLM调用：1次                                              │
└─────────────────────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ 基础有效性校验（规则，无LLM成本）                          │
│ 检查：单品存在、品类基本完整、无重复                       │
└─────────────────────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ Agent 3：评审判定 Agent                                    │
│ 输入：用户请求 + 3-5套方案 + request_signature            │
│ 输出：首选 + 备选 + 评审报告 + 决策分支                   │
│ LLM调用：1次（单次调用双阶段协议）                        │
└─────────────────────────────────────────────────────────────┘
   │
   ├── accept ──────────────► 输出
   ├── recompose ──────────► Agent 2（重新组合）
   ├── retrieve_more ──────► Agent 1（扩展检索）
   └── wardrobe_gap ───────► 最佳可行方案 + 缺失提示

总回退次数：≤1
LLM调用：正常3次 / recompose 5次 / retrieve_more 6次
```


## 三、Agent 1：语义检索 Agent

### 3.1 职责

理解用户完整意图 → 构建请求特异性画像 → 生成多类检索查询 → 调用向量检索工具 → 输出结构化候选池

### 3.2 输入

| 项目 | 说明 |
|------|------|
| 用户请求 | 原始自然语言输入 |
| 衣橱统计摘要 | 品类数量分布，不包含全部单品 |
| 历史推荐摘要 | 最近3次的request_signature和结构签名 |
| 检索工具 | 可调用的向量检索接口 |

### 3.3 输出结构

```json
{
  "request_signature": {
    "theme": "看《悲惨世界》音乐剧",
    "unique_mood": ["悲壮", "克制", "复古文学感"],
    "practical_context": ["剧场", "久坐", "半正式"],
    "generic_tendencies_to_avoid": [
      "仅由基础款组成，缺少能承载主题的视觉重点",
      "组合与普通通勤推荐几乎无差异",
      "只通过理由解释主题，单品本身没有体现"
    ]
  },
  "retrieval_plans": [
    { "type": "core", "query": "深色复古文学感剧场穿搭", "score_weight": 0.40 },
    { "type": "distinctive", "query": "酒红炭灰结构感单品", "score_weight": 0.30 },
    { "type": "supporting", "query": "舒适半正式旧世界质感", "score_weight": 0.10 }
  ],
  "candidate_requirements": {
    "tops": 10,
    "bottoms": 10,
    "dresses": 6,
    "outerwear": 8,
    "shoes": 8,
    "accessories": 8
  }
}
```

### 3.4 候选池构建流程

1. 执行 3 类查询，每类独立检索
2. 按类型标记来源，加权合并
3. 按 `candidate_requirements` 配额截取
4. 合并去重，输出 Top-50

**配额降级逻辑**：若某品类实际数量不足配额，允许配额动态转移至其他品类，同时记录转移日志供 Phase 7 评估。

### 3.5 检索分数计算

```python
final_score = (
    core_similarity * 0.40
    + distinctive_similarity * 0.30
    + supporting_similarity * 0.10
    + preference_score * 0.10
    + novelty_score * 0.10
)
```


## 四、Agent 2：搭配组合 Agent

### 4.1 职责

从候选池中组合多套搭配，体现请求专属语义，避免近期高频结构。

### 4.2 输入

| 项目 | 说明 |
|------|------|
| 用户请求 | 原始自然语言输入 |
| Top-50 候选 | 含品类、颜色、材质、风格等属性 |
| request_signature | 包含 unique_mood 和 generic_tendencies_to_avoid |
| 近期高频结构 | 最近5次的搭配结构签名 |

### 4.3 生成顺序

**先策略，后选品**：
1. 形成 `composition_strategy`（决定表达什么、如何表达）
2. 根据策略选择单品
3. 输出完整方案

### 4.4 输出结构

```json
{
  "outfits": [
    {
      "outfit_id": "outfit_001",
      "composition_strategy": {
        "visual_anchor": "深酒红或炭灰结构感外套",
        "supporting_direction": "克制的浅色内搭与深色下装",
        "practical_balance": "保证剧场久坐舒适，避免过度戏服化"
      },
      "item_ids": ["coat_07", "top_03", "bottom_05", "shoes_02"],
      "style_tag": "剧场复古",
      "reasoning": "炭灰色大衣提供结构化轮廓，配合深酒红内搭体现悲壮感",
      "request_specific_elements": [
        { "item_id": "coat_07", "role": "通过结构感和深色调体现剧场仪式感" }
      ]
    }
  ]
}
```

### 4.5 核心规则

- **禁止**输出候选池外的单品ID
- **避免**近期高频出现的结构签名
- **优先**选择能够体现 `unique_mood` 的单品
- **保留**至少 1 套“更实穿”的备选方案
- `style_tag` 仅作为自然语言摘要和展示字段，不作为固定枚举或硬约束


## 五、Agent 3：评审判定 Agent

### 5.1 职责

比较多套方案，选择最优推荐，判断失败来源。采用**单次LLM调用的双阶段协议**：
- 阶段一：盲评搭配本身（仅依据单品数据，不看reasoning）
- 阶段二：检查 Composer 解释是否有单品依据

### 5.2 输入

| 项目 | 说明 |
|------|------|
| 用户请求 | 原始自然语言输入 |
| 3-5 套方案 | 含 composition_strategy 和 item_ids |
| request_signature | 用于判断还原度 |

### 5.3 评审维度

| 维度 | 权重 | 说明 |
|------|------|------|
| 需求还原度 | 25% | 是否理解了用户完整需求 |
| 请求特异性 | 25% | 是否体现当前问题区别于普通日常的部分 |
| 单品协调性 | 20% | 色彩、材质、廓形是否协调 |
| 实穿性 | 15% | 是否适合真实使用 |
| 新鲜感 | 15% | 是否避免高频重复组合 |

### 5.4 输出结构

```json
{
  "outfit_assessment": {
    "outfit_id": "outfit_002",
    "dimension_scores": {
      "request_relevance": 9,
      "request_specificity": 8,
      "coordination": 9,
      "wearability": 8,
      "freshness": 7
    },
    "reasoning": "通过深色结构感单品表达悲壮氛围，同时保证了实穿性",
    "improvements": "配饰上可增加一枚胸针强化主题"
  },
  "explanation_assessment": {
    "grounded": true,
    "unsupported_claims": []
  },
  "alternatives": [
    { "outfit_id": "outfit_001", "strength": "更实穿" },
    { "outfit_id": "outfit_003", "strength": "更有主题表达" }
  ],
  "decision": "accept"
}
```

### 5.5 决策分支

```json
// 情况A：重新组合（候选池有特色单品但Composer未使用）
{
  "decision": "recompose",
  "failure_source": "composer",
  "feedback": "候选中已有复古外套和酒红单品，但当前方案仍采用普通基础组合"
}

// 情况B：扩展检索（候选池本身缺少特色单品）
{
  "decision": "retrieve_more",
  "failure_source": "candidate_pool",
  "feedback": "候选池缺少能够承载剧场复古氛围的主视觉单品"
}

// 情况C：衣橱缺口（整个衣橱缺少必要品类）
{
  "decision": "wardrobe_gap",
  "failure_source": "wardrobe",
  "feedback": "现有衣橱缺少适合该氛围且满足实穿需求的鞋履",
  "missing_items": [
    {
      "category": "shoes",
      "desired_features": ["深色", "半正式", "复古感"]
    }
  ],
  "best_effort_outfit_id": "outfit_003"
}
```


## 六、推荐多样性控制

### 6.1 请求特异性建模

Agent 1 输出的 `request_signature` 是整个系统的核心控制信号，贯穿三个 Agent：
- `unique_mood`：指导 Agent 2 的选品方向
- `generic_tendencies_to_avoid`：指导 Agent 2 避免泛化组合
- Agent 3 用 `request_signature` 判断“请求特异性”维度

### 6.2 结构签名

为每套搭配生成结构签名，用于跨请求记忆：

```json
{
  "signature": {
    "category_structure": ["outerwear", "top", "bottom", "shoes"],
    "dominant_color_family": ["dark_neutral", "burgundy"],
    "style_mix": ["vintage", "formal"],
    "layer_count": 2
  }
}
```

初版只使用 `category`、`color`、`style`、`formality` 等已有属性构建签名。

### 6.3 跨请求记忆

- 记录最近 5 次的 `request_signature` 和结构签名
- Agent 1 生成检索计划时参考
- 仅对近期曝光做软惩罚，不强制差异化
- 对于高度相似请求（面试/答辩/商务会议），允许合理重合


## 七、评估指标

### 7.1 核心指标

| 指标 | 说明 |
|------|------|
| Cross-request Item Overlap | 不同请求之间的单品重合率 |
| Outfit Signature Repetition | 搭配结构模板重复率 |
| Semantic Match | 请求与搭配的语义匹配度（由独立LLM Judge评估） |
| Human Preference Win Rate | 人类盲评中新方案 vs 旧方案的胜率 |
| Wardrobe Grounding Rate | 推荐单品是否真实存在于衣橱（目标100%） |

### 7.2 实验假设

对不同请求分类验证：

- 相似请求对（面试、答辩、商务会议）
- 相关请求对（音乐节、海边、户外）
- 不相关请求对（面试、海边）

**预期关系**：

```
Overlap(不相关) < Overlap(相关) < Overlap(相似)
```

实验后根据数据分布确定具体阈值，不提前固定。


## 八、场景效果预期

| 用户输入 | 原方案已知问题 | 新方案预期改善 |
|---------|--------------|--------------|
| “面试穿什么” | 商务正装，基本正确 | 保持不变，可能纳入衣橱真实单品 |
| “悲惨世界穿什么” | 被压缩为普通演出 | 保留作品氛围和剧场语义 |
| “周杰伦演唱会穿什么” | 回退为日常休闲 | 提取街头、复古、活动舒适性 |
| “美拉德穿搭” | 依赖新增规则 | 利用模型知识或风格RAG理解 |
| “薄荷漫波穿搭” | 无固定映射 | 通过模型理解或外部知识补充 |
| “明天下小雨穿什么” | 需额外天气模块 | 理解湿滑、防泼水、裤脚和鞋履实用性需求 |
| “高考穿什么” | 无法映射→日常 | 理解长时间坐着、温度变化、舒适、不分散注意力，以及可能存在的心理仪式需求 |


## 九、与旧方案对比

| 维度 | 原方案（v3.1） | 新方案（v3.2.1-final） |
|------|---------------|----------------------|
| Agent/模块数量 | 7+ | **3** |
| 是否需要场合映射表 | ✅ 需要手动维护 | ❌ **不需要** |
| LLM 调用次数 | 5-7 次 | **3-6 次** |
| 信息处理方式 | 拆解为标签→丢失信息 | **直接语义理解→保留信息** |
| 新场景泛化 | 差（需手动添加映射） | **好（LLM直接理解）** |
| 跨请求多样性 | 差（反复输出日常搭配） | **好（请求特异性建模）** |
| 评审方式 | 确定性规则 | **LLM 5维度评审** |
| 衣橱不足处理 | 候选枯竭 | **最佳可行方案 + 缺失提示** |
| 规则维护 | 持续维护场景规则和评分矩阵 | **维护衣橱数据和风格知识，规则成本显著降低** |

## 十一、已解决的问题

| 问题 | 解决方案 |
|------|----------|
| 信息损耗 | Agent 1 保留完整语义，输出 request_signature |
| 场景覆盖不全 | 语义理解，无需映射表 |
| 推荐重复 | 跨请求记忆 + 结构签名 + 软惩罚 |
| 衣橱不足 | 降级方案 + 缺失提示（wardrobe_gap分支） |
| 新风格响应 | LLM 预训练知识 + 外部知识源 |
| 请求特异性不可计算 | distinctive_similarity 替代抽象分数 |
| 候选池品类失衡 | 动态品类配额 + 降级转移 |
| 评审文案偏见 | 单次调用双阶段协议（盲评搭配→检查解释） |
| 回退指向不准确 | Critic 区分 recompose / retrieve_more / wardrobe_gap |
| LLM调用统计错误 | 修正为 3/5/6 次 |
