# StyleForge v4.0：个人衣柜多智能体穿搭决策系统

> 文档类型：个人项目技术计划与实施规格  
> 日期：2026-07-22  
> 目标：构建一个可本地运行、可量化评测、可用于实习求职展示的多智能体穿搭系统。

## 1. 执行摘要

StyleForge 接收用户的自然语言穿搭需求，只从该用户实际拥有且当前可用的衣物中生成三套搭配，并给出约束检查、分项评分、选择理由和可替代单品。

系统不是“让多个大模型分别扮演时尚顾问”，而是由三个具有不同决策职责的 LLM Agent，与确定性的约束、检索、评分和局部搜索工具共同组成。LLM 负责理解模糊语义和解释决策；代码负责保证衣物真实存在、硬约束不被违反、结果可以复现和评测。

数据分为三层：

1. **用户个人衣柜**：运行时唯一允许推荐的单品池。
2. **Polyvore / Garments2Look-Polyvore**：离线学习搭配兼容性和构建评测集。
3. **Garments2Look 的人物 Look 与分割标注**：仅作为未来虚拟试穿扩展，不进入 MVP。

项目首版不做衣物生成、不做虚拟试穿、不训练大型视觉模型。首版重点是完整闭环、可解释约束、可靠降级、离线评测和可演示的工程质量。

## 2. 项目目标与边界

### 2.1 核心用户故事

用户完成衣柜录入后，可以输入：

> 明天 12℃，我要参加互联网公司的面试，希望正式但不要太老气，不穿高跟鞋。

系统应：

1. 识别面试、温度、正式度、风格和禁选项。
2. 发现缺少的关键上下文时最多追问一次。
3. 只使用用户衣柜内可用的单品。
4. 生成三套有明显差异的完整搭配。
5. 展示每件单品、约束检查、评分、搭配理由和替代项。
6. 衣柜无可行组合时明确说明缺少什么，而不是输出违规方案。

### 2.2 MVP 范围

- 用户衣物图片上传、自动标注和人工校正。
- 自然语言需求解析。
- 场合、天气、正式度、品类、禁选和必选约束。
- 分槽位候选检索与组合搜索。
- 三 Agent 协作和确定性 Critic/Repair 闭环。
- SQLite 持久化、运行日志和反馈记录。
- FastAPI 后端和 Streamlit 演示界面。
- Polyvore 兼容性基线与离线评测。

### 2.3 非目标

- 不在 MVP 中生成新衣服图片。
- 不在 MVP 中生成用户穿上搭配后的虚拟试穿图。
- 不进行人脸、身材或吸引力评价。
- 不假设服装具有固定性别；只使用用户明确提供的偏好和尺码信息。
- 不将数据集中的随机商品直接称为用户个人衣柜。
- 不为追求“Agent 数量”拆分没有独立决策职责的节点。

## 3. 总体架构

```text
用户 / Streamlit
       |
       v
FastAPI API --------------- SQLite / 本地图片目录
       |
       v
LangGraph Supervisor + SQLite Checkpointer
       |
       +--> Planner Agent
       |       |
       |       +--> Context / Weather Tool
       |       +--> User Preference Store
       |
       +--> Constraint Compiler（确定性）
       |
       +--> Slot Retriever + Candidate Generator（确定性）
       |       |
       |       +--> Wardrobe Repository
       |       +--> Embedding Index
       |       +--> Compatibility Model / Prior
       |
       +--> Stylist Agent
       |
       +--> Score Engine（确定性硬门禁 + 软评分）
       |
       +--> Reviewer Agent
               |
               +--> Repair Search Tool（确定性局部搜索）
               +--> Accept / Repair

Supervisor 在候选为零时确定性地产生 Infeasible，不经过 Reviewer。
```

### 3.1 组件分类

| 组件 | 类型 | 是否调用 LLM | 最终权限 |
|---|---|---:|---|
| Planner Agent | Agent | 是 | 生成结构化任务、决定是否追问 |
| Stylist Agent | Agent | 是 | 从合法候选中选择并排序 |
| Reviewer Agent | Agent | 是 | 接受结果或请求局部修复、生成最终说明 |
| Constraint Compiler | Tool/Service | 否 | 编译硬约束和软偏好 |
| Slot Retriever | Tool/Service | 否 | 分槽位召回候选 |
| Candidate Generator | Tool/Service | 否 | 生成完整搭配组合 |
| Score Engine | Tool/Service | 否 | 硬约束门禁和版本化评分 |
| Repair Search | Tool/Service | 否 | 单槽位局部替换与防循环 |
| User Preference Store | Repository | 否 | 保存显式偏好和反馈 |

### 3.2 Agent 的真实独立职责

#### Planner Agent

输入：用户需求、用户显式偏好、可选的时间和天气上下文。  
输出：严格符合 `TaskSpec` Schema 的结构化任务。

Planner 只负责语义理解，不直接选择衣物。缺少地点、时间、场合或必需品类等关键条件时，最多生成一个合并后的追问；非关键缺失项使用显式默认值，并在输出中记录假设。

#### Stylist Agent

输入：已通过硬过滤的候选搭配摘要、软偏好、差异化要求。  
输出：候选组合 ID 的排序和简短风格意图。

Stylist 不能自由输出衣物 ID。其 Schema 只能引用 `candidate_outfit_ids` 中已存在的值。若输出非法 ID，结构校验立即失败并回退到确定性排序。

#### Reviewer Agent

输入：搭配、硬约束报告、分项软评分、已执行修复历史。  
输出：`accept` 或 `repair`，以及面向用户的解释草稿。

Reviewer 不能覆盖硬约束门禁，不能自行修改分数。它只能基于 Score Engine 提供的结构化事实申请调用 Repair Tool。

`infeasible` 只由确定性工作流在候选为零时产生。Reviewer 接收的搭配已经通过硬门禁，因此无权将主观不满意改写成“无可行方案”。Reviewer 对每个成功请求至少调用一次；发生 Repair 时才产生额外 Reviewer 调用。

## 4. LangGraph 工作流

```text
START
  -> load_user_context
  -> planner_agent
  -> [need_clarification?]
       yes and clarification_count == 0 -> interrupt_and_ask -> planner_agent
       yes and clarification_count >= 1 -> apply_documented_defaults
       no  -> compile_constraints
  -> retrieve_by_slot
  -> generate_candidates
  -> [candidate_count == 0?]
       yes -> build_infeasible_response -> persist_run -> END
       no  -> score_all_candidates
  -> retain_top_hard_valid_candidates
  -> [hard_valid_candidate_count == 0?]
       yes -> build_infeasible_response -> persist_run -> END
       no  -> stylist_agent
  -> select_diverse_top_n
  -> reviewer_agent
  -> [review_decision]
       accept     -> build_response -> persist_run -> END
       repair     -> [iteration >= 2?]
                       yes -> select_best_hard_valid_results -> build_response -> persist_run -> END
                       no  -> repair_search -> score_repaired_outfits -> improvement_guard
  -> [improved_by_epsilon?]
       yes -> increment_iteration -> select_diverse_top_n -> update_diversity_report -> reviewer_agent
       no  -> select_best_hard_valid_results -> build_response -> persist_run -> END

ANY NODE EXCEPTION
  -> record_failure_event
  -> persist_failed_run
  -> END
```

### 4.1 GraphState

```python
class GraphState(BaseModel):
    run_id: str
    thread_id: str
    user_id: str
    user_query: str

    task_spec: TaskSpec | None = None
    assumptions: list[str] = Field(default_factory=list)
    clarification_question: str | None = None
    clarification_count: int = 0

    hard_constraints: list[Constraint] = Field(default_factory=list)
    soft_preferences: list[Preference] = Field(default_factory=list)
    slot_template: SlotTemplate | None = None

    candidate_item_ids_by_slot: dict[str, list[str]] = Field(default_factory=dict)
    candidate_outfit_ids: list[str] = Field(default_factory=list)
    selected_outfit_ids: list[str] = Field(default_factory=list)
    scorecards: dict[str, ScoreCard] = Field(default_factory=dict)
    diversity_report: DiversityReport | None = None

    iteration: int = 0
    seen_outfit_signatures: set[str] = Field(default_factory=set)
    best_total_by_outfit: dict[str, float] = Field(default_factory=dict)
    last_score_delta: float | None = None
    status: Literal["running", "waiting", "accepted", "infeasible", "failed"] = "running"

    trace_events: list[TraceEvent] = Field(default_factory=list)
```

GraphState 只保存 ID、Schema 和评分，不保存图片二进制、模型对象或完整 embedding。候选组合在 `CandidateOutfitRepository` 中以 `run_id + outfit_id -> ordered item_ids` 持久化，Score Engine、Reviewer 和 Repair 通过 Repository 解析 outfit ID。图片和向量同样由 Repository 通过 item ID 读取。所有成功、无解、降级、Repair 停止和异常失败路径都必须持久化，保证运行记录完整。Supervisor 在最外层使用统一异常边界，任何未处理异常都先写入失败事件，再将状态保存为 `failed`。

## 5. 约束体系

### 5.1 硬约束

硬约束不参与加权评分，任何一项失败即淘汰：

- 单品属于当前用户。
- 单品状态为可用且未标记为待清洗、借出或收纳不可取。
- 单品 ID 存在，图片和元数据可读取。
- 满足所选穿搭模板的核心槽位。
- 满足用户明确的必选、禁选、品类、颜色和材质要求。
- 满足明确的天气安全限制，例如低温保暖或降雨防水要求。
- 同一套搭配不得重复使用同一单品。

硬约束不足以产生任何组合时，系统返回 `infeasible`，并列出导致无解的阻塞约束和建议放宽项。

这里不承诺求解计算代价高且定义容易混淆的“最小约束集合”。系统实际返回 `blocking_constraints`：

1. 先对可由用户放宽的约束逐项做删除测试，得到 `single_removal_blockers`。
2. 若单项测试为空且可放宽约束不超过 12 个，再对约束对做有界二项删除测试，得到 `pair_removal_blockers`。
3. 若仍无结果，返回“存在多约束交互阻塞”，列出当前约束和各槽位剩余候选数，请用户选择放宽方向，不伪称已经找到最小集合。

结果按用户优先级排序。用户归属、数据隔离和安全约束不进入自动放宽列表；存在多个阻塞项时全部展示。

当显式硬约束依赖未知或低置信度属性时，默认将该单品视为“不满足”，不能凭模型猜测通过。若这导致无解，系统请求用户补充该属性或明确允许未知值；安全相关属性未知时始终排除，不能降为软偏好。

### 5.2 软偏好

- 场合与正式度接近程度。
- 风格语义匹配。
- 色彩协调。
- 学习到的搭配兼容性。
- 用户历史显式偏好。
- 天气和活动实用性。
- 新颖性与近期穿着重复度。
- 三套推荐之间的差异化。

### 5.3 穿搭模板

```yaml
templates:
  two_piece:
    required_slots: [top, bottom, shoes]
    optional_slots: [outerwear, bag, accessory]
  dress:
    required_slots: [dress, shoes]
    optional_slots: [outerwear, bag, accessory]
  layered:
    required_slots: [inner_top, outer_top, bottom, shoes]
    optional_slots: [coat, bag, accessory]
```

模板选择由 Constraint Compiler 根据场合、天气和衣柜覆盖情况确定，而不是由 LLM 自由发明槽位。

## 6. 候选检索与组合生成

### 6.1 分槽位检索

禁止使用一个全局 Top-30 列表。每个必需槽位独立检索：

1. 应用硬约束。
2. 计算文本/图片向量与 `TaskSpec` 的相似度。
3. 加入正式度、天气、用户偏好等轻量排序分。
4. 每个必需槽位保留 Top-K，默认 `K=8`。
5. 可选槽位默认 `K=4`，允许为空。

### 6.2 组合搜索

对于个人衣柜，采用 beam search 而不是让 LLM逐件挑选：

1. 按必需槽位顺序逐步扩展。
2. 使用品类共现先验、颜色规则和兼容性模型做中间剪枝。
3. Beam 宽度初始设为 30，通过评测调整。
4. 将每个组合写入 `CandidateOutfitRepository`，完成去重，并为所有组合计算最终 ScoreCard。
5. 先按硬门禁和确定性总分保留前 10～20 个合法组合，再交给 Stylist Agent 排序。
6. Stylist 给出排序后，由确定性 `DiverseSetSelector` 选择最多三套结果，不能绕过 Score Engine。

当衣柜小于 500 件时，可直接在内存计算候选；FAISS 主要用于离线数据集和未来多用户扩展，不作为 MVP 的强依赖。

## 7. 评分与 Critic 设计

### 7.1 ScoreCard

```python
class ScoreCard(BaseModel):
    outfit_id: str
    scorer_version: str
    hard_passed: bool
    hard_violations: list[Violation]

    context_match: float
    compatibility: float
    color_harmony: float
    preference_match: float
    practicality: float
    novelty: float
    total: float

    evidence: list[ScoreEvidence]
```

所有软评分字段及 `total` 均使用闭区间 `0～100`。100 表示在该评分版本下最符合目标，0 表示完全不符合。各分项必须在计算时裁剪到该区间，`total` 也是相同量纲。Repair 的 `epsilon=1.0` 因而表示总分至少提高 1 分。

### 7.2 初始软评分

```text
total =
    0.30 * context_match
  + 0.25 * compatibility
  + 0.15 * color_harmony
  + 0.15 * preference_match
  + 0.10 * practicality
  + 0.05 * novelty
```

权重只是 `scorer_v1` 的初始配置，必须在验证集和人工评价中校准。Skill、Palette、材质和正式度不再作为重复维度；它们分别成为硬约束或上述单一维度的证据。

当学习模型不可用时，`compatibility` 使用 Polyvore 品类/标签共现先验。降级评分必须使用不同的 `scorer_version`，避免把两种分数直接比较。

### 7.3 通过规则

- `hard_passed` 必须为真。
- 三套结果按总分排序，但不使用未经校准的固定 75 分阈值。
- 如果只有一到两套硬合法组合，可以少于三套输出，并说明衣柜覆盖不足。
- 评分解释必须引用具体衣物属性和规则证据，不能生成无法验证的时尚结论。

### 7.4 结果集差异化

差异化是结果集级约束，不重复加入单套 ScoreCard：

- `DiverseSetSelector` 依次选择排名最高、且与已选方案差异满足阈值的组合。
- 单品集合使用 Jaccard 距离，风格使用 embedding 余弦距离，模板和主色变化作为附加证据。
- `diversity_target=low/medium/high` 映射到版本化阈值配置。
- 若无法满足目标，允许减少输出数量或返回最接近结果，并在 `DiversityReport` 中说明。
- 评测报告记录平均两两距离、重复单品率和三套方案的模板覆盖数。

## 8. Repair 设计

Repair 是确定性的单槽位局部搜索：

1. 从 ScoreCard 找到主要问题和涉及槽位。
2. 在同槽位合法候选中尝试替换一件单品。
3. 对新组合重新执行全部硬约束和软评分。
4. 仅接受总分提高至少 `epsilon=1.0` 的替换。
5. 将排序后的衣物 ID 组合计算为签名，已出现签名不得再次进入。
6. 每个推荐请求最多执行两轮 Repair。
7. 连续一轮无改善立即停止。

Repair 只能放宽被标记为软偏好的条件。用户明确的禁选、必选和安全约束永不自动放宽。

## 9. 数据策略

### 9.1 三层数据边界

| 数据层 | 内容 | 用途 | 是否直接推荐给用户 |
|---|---|---|---:|
| Personal Wardrobe | 用户上传并确认的衣物 | 在线候选池 | 是 |
| Compatibility Corpus | Polyvore / Garments2Look-Polyvore | 训练先验、兼容性模型、离线评测 | 否 |
| VTON Extension | Look 图片、Mask、穿着效果 | 未来虚拟试穿 | 否 |

### 9.2 当前 Polyvore 数据问题

现有本地 Polyvore 图片覆盖不足：很多搭配只剩一到两件可用图片，包含上衣和下装的有效搭配约 50 套。该规模只适合冒烟测试，不能支撑视觉兼容性训练，也不能作为完整的端到端评测集。

因此：

- 现有 Polyvore JSON 可继续用于结构、品类和共现统计。
- 只有通过图片完整性门禁的样本才进入视觉训练或评测。
- 不再将当前数据准备状态标记为“Phase 0 已完成”。
- 不以“已有 1100 件衣物”等未经审计的数量作为计划依据。

现有本地 Polyvore 与 Garments2Look-Polyvore 可能来自相同上游语料，但 ID、筛选和图片组织方式不保证完全一致。视觉语料以 Garments2Look-Polyvore 的两个 JSON 和商品图归档为唯一规范来源；现有本地数据只作为辅助对照，不直接与规范语料拼接。确需映射时，必须使用 source ID、规范化类别和图片 pHash 建立显式映射表，并在映射后重新执行跨划分去重，不能按文件名相似直接合并。

截至 2026-07-22 的实际审计结果如下：

- `polyvore_image_v1.0_2512.json` 含 126,928 件商品，核心字段无缺失、无重复 item ID，所有记录声明了商品图；由于图片不在本机，这只证明元数据声明完整，126,928 件均标记为 `image_status=unbound`。
- `polyvore_outfit_v1.0_2512.json` 含 18,086 套 outfit 和 93,305 条关系，其中 8,596 个 item ID 不在商品元数据目录，影响 8,292 套 outfit。
- 严格执行“全部 item 都存在才导入”后，得到 9,794 套完整 outfit、46,413 条关系，其中 train 9,556 套、test 238 套；包含 5,466 套 `top + bottom + shoes` 和 3,303 套 `one_piece + shoes`。
- 93,305 个 outfit item ID 均只属于一个 outfit，没有跨 outfit 复用。因此不能依赖 item-ID 协同过滤或 item-pair 频次泛化；outfit 只作为集合级正样本，模型必须依赖类别、文本或视觉特征。
- 图片存在性、解码和 pHash 门禁尚未执行，视觉训练仍处于阻塞状态。

### 9.4 数据质量门禁

每个样本必须记录拒绝原因。质量审计至少输出：

- 总搭配数。
- 每类穿搭模板的数量。
- 单品引用数和唯一单品数。
- 图片存在率、损坏率和可解码率。
- 必需槽位覆盖率。
- 品类、性别标签、季节和风格分布。
- 重复 ID、重复图片 pHash 和跨划分重复情况。
- 训练、验证和测试划分数量。

进入视觉兼容性训练的样本必须满足：

```text
two_piece: top + bottom + shoes 的图片全部存在
dress: dress + shoes 的图片全部存在
all_required_images_decodable == true
no_duplicate_item_in_outfit == true
```

处理规模分级：

- 50 套：只能用于管线冒烟测试。
- 少于 500 套：不训练视觉兼容性模型，只使用规则、文本标签和品类共现。
- 500～4999 套：可训练探索性的轻量模型，但必须进行重复划分或交叉验证，并将结果标记为小样本实验。
- 5000 套以上：可将冻结 embedding 上的兼容性模型作为正式对比实验。

数量门槛与单样本门禁同时满足后才能进入对应训练路线；数量达标不能替代图片可解码、槽位完整和防泄漏要求。

### 9.5 数据划分与泄漏控制

- 优先保留官方 train/test 标记。
- 从训练部分按 outfit ID 建立验证集。
- 使用单品 ID 和图片 pHash 检查跨划分重复。
- 论文对齐评测使用官方划分；另建 cold-item 划分评估新单品泛化。
- 任何人工构建的演示衣柜不得出现在模型测试标签中。

### 9.6 演示个人衣柜

首版准备一个独立的 40～80 件演示衣柜：

- 至少覆盖上装、下装、连衣裙、鞋、外套和配饰。
- 至少存在 20 套可被规则确认的完整组合。
- 图片、类别和关键标签全部人工复核。
- 数据集来源单品仅用于本地演示并保留来源与许可信息。
- 正式演示同时支持用户上传自己的 5～20 件衣物。

## 11. 视觉与兼容性模型

### 11.1 MVP 基线

- MVP 默认使用 `patrickjohncyh/fashion-clip` 生成冻结 embedding；其他模型只能作为单独版本的对比实验，不能在同一索引中混用。
- 图片颜色通过确定性图像算法提取，并允许用户纠正。
- 材质和风格标签由视觉模型建议、用户确认。
- Polyvore 训练搭配计算品类共现和标签共现先验。
- 不微调视觉主干。

默认 embedding 配置固定为：

```yaml
model_id: patrickjohncyh/fashion-clip
model_revision: 7e3ba62ce16b379a1ab479346b66f192e76f51b7
weight_format: safetensors
processor_revision: 7e3ba62ce16b379a1ab479346b66f192e76f51b7
image_size: 224
projection_dim: 512
output_dtype: float32
normalization: l2
embedding_version: fashionclip2-7e3ba62-l2-v1
```

`artifacts/embedding_manifest.json` 还必须保存实际的 `transformers`、`torch`、Pillow 版本、处理配置哈希、生成时间、输入数据 revision 和单品 ID 顺序。更换任一模型、预处理或归一化参数都必须生成新的 embedding 版本和独立索引。

### 11.2 学习型兼容性模型

仅当完整图片搭配达到质量门禁后训练：

- 输入：冻结的单品图片 embedding、品类 embedding 和少量数值特征。
- 正样本：完整真实搭配。
- 负样本：保持槽位结构的同品类替换，不使用明显错误的随机品类作为唯一负样本。
- 模型：轻量 MLP、DeepSets 或小型 Set Transformer。
- 输出：搭配兼容性概率。
- 对比：规则基线、品类共现基线、embedding 相似度基线。

兼容性模型只提供软分数，不能覆盖用户硬约束。

## 14. 稳健性与降级

| 故障 | 检测 | 降级策略 |
|---|---|---|
| LLM 超时 | timeout | 重试一次；失败后使用结构化表单或默认 TaskSpec |
| LLM Schema 非法 | Pydantic 校验 | 带错误信息重试一次；再次失败进入规则模式 |
| Stylist 输出非法 ID | allow-list 校验 | 使用确定性总分排序 |
| Embedding 模型不可用 | 健康检查 | 使用标签、品类和规则检索 |
| 兼容性模型不可用 | 模型加载失败 | 使用品类/标签共现先验，并切换 scorer 版本 |
| 候选为零 | candidate_count | 返回有界阻塞诊断和放宽建议 |
| Repair 循环 | 组合签名 | 禁止访问旧签名，立即停止无改善分支 |
| 数据文件损坏 | 哈希/图片解码 | 隔离坏文件并生成审计报告 |
| SQLite 锁冲突 | 数据库异常 | 短暂重试、缩短事务；未来升级 PostgreSQL |

任何降级都必须写入 `trace_events` 并在调试视图可见。

## 16. 测试与评测

### 16.1 单元测试

- Schema 边界和非法输入。
- 品类规范化和模板槽位。
- 硬约束永不被软分数覆盖。
- 显式硬约束依赖未知/低置信度属性时默认不能通过。
- 色彩距离、正式度和天气规则。
- 候选生成不重复单品。
- ScoreCard 权重与版本。
- Repair 单调改善、防循环和最大轮数。
- Repair 后重新计算结果集差异化报告。
- 单项和二项约束删除诊断能够识别交互阻塞。
- Repository 事务和用户数据隔离。
- CandidateOutfitRepository 能按 `run_id + outfit_id` 恢复有序单品列表。
- 成功、无解、降级、Repair 停止和异常失败路径都写入运行记录。

### 16.2 Agent 合同测试

- Planner 输出固定 Schema。
- 缺少关键信息时通过 `clarification_count` 保证最多追问一次。
- Stylist 只能引用候选 ID。
- Reviewer 只能输出 `accept` 或 `repair`，且不能接受硬约束失败的搭配。
- 模型超时、拒绝和非法 JSON 均有可验证降级。
- 使用录制的固定响应进行离线回归测试，避免测试依赖实时 API。

### 16.3 离线评测

| 能力 | 数据 | 指标 |
|---|---|---|
| 意图解析 | 50～100 条人工标注中文需求 | 字段 Precision/Recall/F1、Schema 成功率 |
| 槽位检索 | 完整搭配留一件评测 | Recall@K、MRR、槽位覆盖率 |
| 兼容性 | 正负搭配测试集 | Accuracy、ROC-AUC、PR-AUC |
| 规则门禁 | 合成边界案例 | 硬约束违规数必须为 0 |
| Repair | 人为破坏的搭配 | 平均分数增量、成功率、循环率 |
| 端到端 | 30～50 条真实需求 | 完成率、p50/p95 延迟、LLM 调用次数 |

兼容性模型必须与以下基线对比：

1. 随机排序。
2. 品类共现。
3. 规则评分。
4. Fashion embedding 相似度。
5. 学习型兼容性模型。

不预先编造“准确率达到 80%”等结果。成功标准是报告可复现指标，并证明最终方案在至少一个核心指标上稳定优于简单基线，同时保持零硬约束违规。

### 16.4 人工评价

- 评价者看不到方案来自哪个系统版本。
- 对规则基线与完整系统进行 A/B 选择。
- 评价场合匹配、整体协调、实用性、解释可信度和三套多样性。
- 单独记录“无可行方案”的判断是否正确。
- 公开样本量、评价问题和失败案例，不只展示成功截图。

## 17. 安全、隐私与许可

- 用户图片默认保存在本地目录。

## 19. 主要风险与决策

| 风险 | 影响 | 处理 |
|---|---|---|
| Garments2Look 商品图片仍不完整 | 无法训练视觉兼容性模型 | 质量门禁；低于 500 套则只做规则/共现基线 |
| 下载或解压空间不足 | 数据准备失败 | 下载前 dry-run；只取商品图和元数据；不取 Look |
| 数据集时尚风格存在年代/平台偏差 | 泛化有限 | 用户反馈、人工演示衣柜、明确报告数据偏差 |
| 材质无法可靠从图片判断 | 规则产生假精确 | 标记置信度；让用户校正；低置信度属性不能作为满足显式硬约束的证据 |
| LLM 生成不稳定 | 非法状态或延迟 | 严格 Schema、allow-list、一次重试、规则降级 |
| 多 Agent 增加成本和延迟 | 演示体验下降 | 最多三个 LLM 阶段；缓存；Reviewer 首次固定调用一次，仅 Repair 后追加调用 |
| 评分缺乏公认真值 | 无法证明效果 | 基线、官方任务、人工 A/B、消融和失败案例共同评估 |
